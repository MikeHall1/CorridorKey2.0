# Explicit resource snapshots

The desktop **Resources…** window samples the owned render worker or a chosen containing filesystem. Sampling is explicit; there is no recurring resource query, automatic memory profile, allocation limit, cache eviction or job-size estimate.

**Sample worker** uses the existing framed `status` request. It can start the lazy worker connection, but never submits a render or loads a model. The response includes the actual worker PID, generation, time, current/pending request metadata and sampled resources. Stop, queue changes, connection failure and shutdown preserve the existing ownership barriers. A stopped connection must be replaced explicitly; unavailable snapshots are not retried automatically. An outstanding request must finish or its connection be stopped before another is sent. Benchmark ownership rejects worker sampling.

Process `peak_rss_bytes` is the lifetime maximum resident set of that worker process, not current RSS, all descendants, whole-machine RAM or a hard limit. macOS bytes and Linux KiB conversion are explicit; unsupported platform units/imports return NOT VERIFIED. Windows process-memory support and target-platform behavior remain unverified. The GUI summarizes MiB while retaining exact bytes and provenance in details.

CUDA fields cover the current device's **PyTorch allocator only**: allocated, reserved and lifetime peak allocated bytes. Sampling only consults Torch already loaded in the worker and never imports it or initializes a CUDA context. Without an initialized context, fields are null/NOT VERIFIED. Partial imports/native probe failures also return explicit unavailable metrics. Samples are unsynchronized and can change between fields. They exclude other processes, external/driver allocations and total device/free memory. Real GPU resource sampling remains NOT VERIFIED on this CPU-only host; mocked API tests prove the call contract only. Actual backend availability remains separately inspected through Local assets.

**Sample filesystem** resolves a chosen path and measures the containing filesystem at its nearest existing ancestor (or file parent), off the GUI thread. It creates no directory and scans no tree. Total/used/free bytes and measured path/time are reported; GiB is a display conversion. Free space is not reserved, is not a managed cache-size calculation, and cannot prove a render fits. Another process can change availability immediately. Native filesystem I/O may block; the window remains responsive and waits for the owned I/O before closing. Status/detail text has explicit display bounds.

Milestone23 uses actual owned child status and filesystem calls in tests and the generated desktop workflow. `benchmark-results/m23-generated-summary.json` records no active/pending worker job, null CUDA allocator metrics, an actual worker peak RSS snapshot, an unchanged history database, no directory created and clean worker shutdown. These are resource/ownership observations, not inference speed or quality evidence. See the current checkpoint for complete checks and external limits.
