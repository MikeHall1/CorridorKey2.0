# Developer benchmark window

Open the optional desktop with `python -m corridorkey.desktop`, then **Developer benchmarks…**. This modeless window uses the existing `python -m corridorkey.benchmark --manifest PATH --output PATH` runner. It introduces no alternate inference implementation, fixture backend, made-up metrics or automatic model downloads. The headless command remains usable separately.

Select a real benchmark manifest and an existing output parent. The manifest selects CPU correctness or CUDA inference, at least three repetitions, cold-process/warm-session policy, batch profiles and optional reference-quality manifests. Edit those documented manifests to change processing profiles. The window does not silently replace settings or add outputs. Example manifests and exact measurement contracts are in [benchmark.md](benchmark.md).

**Run** requires render jobs to be terminal. It stops the resident render worker asynchronously, waits for clean bridge completion, then launches one owned benchmark process. A failed/uncertain render-worker shutdown prevents benchmark startup. Rendering and New worker are blocked while a benchmark waits/runs/cancels; after completion explicitly select New worker to resume rendering. No job is automatically resubmitted. Benchmark cleanup uncertainty prevents another processing owner from starting. This is application-local exclusion, not a global GPU lock against other applications or independently launched CLIs.

Each run receives a new `benchmark-UUID/report.json` destination beneath the selected parent. Existing reports/source manifests are not overwritten. Actual inference exports continue to use the existing runner's fresh `benchmark-results/inference-*` directories, referenced in `artifact_dir`; the report parent is not a storage sandbox or disk budget. Keep source, manifest, model and reference files stable for a run. Reports contain the runner's actual hashes/environment/cache conditions/settings and errors; the desktop does not independently authenticate externally edited reports.

The UI displays actual process PID/exit/status, a bounded console tail and the real local report. CPU/repetition phase messages come from the actual runner outside measured scopes. Timings, resources, requested/effective settings, Quick Key work diagnostics and quality fields appear only if the report recorded them. stdout/stderr copies are omitted from the structured inspection view; the full report retains them. Missing measurements stay null/unavailable. **CPU test-process duration is not GPU inference FPS or model-output quality.** Throughput manifests reject `profile_stages=true`; use the existing render profiling option for separate detailed diagnostics.

**Cancel** sends cooperative SIGINT to the owned POSIX process group, then force-stops it after the default five-second grace if needed. The owner observes the same process until it is terminal; observation does not restart or resubmit it. CPU interruptions/timeouts now retain completed repetition records, mark cancelled/failed and leave aggregate timings null unless all required repetitions succeed. Inference cancellation retains the existing report semantics. Interrupting startup/provenance or force-stopping native work may leave no report and partial outputs; the UI states this explicitly. A validated report and process exit0/summary success are required for a complete task. Cleanup errors make controller status failed even if a completed report exists; report contents are preserved as historical evidence.

POSIX force-close covers the live owned process group, including tested signal-ignoring descendants; the leader is reaped and the log thread joined. Cleanup attempts all process/group/log/pipe steps even if group observation fails. Unavailable postmortem inspection remains explicit, as in `HEALTH-ENV-059`; no process-table certification is claimed. Windows uses a new process group, CTRL_BREAK request and live-tree taskkill fallback, but **Windows descendant containment/Job Objects and target behavior are NOT VERIFIED**. This is not complete Windows release acceptance.

**Inspect report…** loads an existing actual report; **Baseline…** displays another report independently. Conditions/results remain separate. This provides manual inspection, not automated alternating A/B experiments, a derived speedup or an assertion of comparable hardware/settings. No category/worst-case or blinded quality verdict is invented. **Export report…** validates and copies exact report bytes to a new `.json` file, using exclusive creation. Existing files are rejected. Report read/export runs off the event thread. Application close cancels processing and waits asynchronously for owned benchmark and active report I/O; native filesystem I/O cannot be forcibly cancelled by the thread.

Console tail retention is64×4096 decoded-byte chunks (at most256KiB of source log bytes, with replacement for split/invalid UTF-8). Report inspection reads at most32MiB and128 nesting levels, rejects duplicate/nonfinite/exponent-overflow values and invalid schema/kind/summary/run types, and limits displayed text to2Mi characters with an explicit truncation note. The original local report is never truncated by the viewer. These are inspection/transport bounds, not whole-process RAM/VRAM, subprocess capture, artifact-storage or source-decoding limits. The existing runner still captures per-repetition test/cold-child logs in its report.

The panel hides when its own window closes; an active benchmark continues under the main workspace's ownership. Use Cancel to stop it. Closing the main workspace waits for owned work cleanup. Closing or reopening a project does not rerun a benchmark. Developer mode is a diagnostic interface, not a security boundary.

The regression suite exercises: real owned-process logs/report/export, cooperative production CLI cancellation, forced ignoring-leader/descendant teardown, crash, finite/depth/size bounds, cleanup-denial fault injection, offscreen UI ownership/cancel/close/report/baseline paths, and production runner preflight failure. Fixture reports are explicitly test-only and contain no invented measured durations. Actual CPU correctness repetitions remain distinct from inference. Interactive native dialogs/OS behavior, Windows packaging/containment, pretrained GPU speed/quality and Resolve acceptance remain **NOT VERIFIED**.

The paired protocol below supplies controlled alternating comparisons. Evaluation dossier mechanics are locally verified in M38; actual held-out/blinded evaluation, richer report history, complete resource telemetry and target packaging remain open. The full development brief remains open.


Paired manifests (kind=inference_pair) now use the same developer-panel Run/Cancel/inspect/export workflow. The owned background task detects protocol using bounded manifest I/O, then dispatches the paired companion. Controlled pairs require manual scheduling, complete matched requested/effective settings and stable per-side repetition conditions; incomplete or mismatched measurements cannot publish a speedup. See benchmark-pairs.md for manifest, timing/warmup/cache scopes and unavailable GPU/quality acceptance.


**Evaluation dossier…** opens a separate background-I/O workflow over explicitly selected existing paired reports. It maps cases/categories/splits, presents comparable metric coverage and worst relative/absolute errors, and exports fresh analysis JSON/HTML/CSV plus an optional assignment-blinded raw-media packet. It never runs inference or invents reviewer ratings. Metadata-only default and explicit media byte ceilings, source preservation, interpretation limits and CLI commands are documented in [evaluation-dossiers.md](evaluation-dossiers.md). Benchmark/inspection startup excludes a live or pending-result dossier owner; workspace close cancels and waits for the actual owner. M38 mechanics are locally verified; actual human review remains pending.
