# Resolve integration — experimental cached-frame adapter; host acceptance unverified

Initial proposed target: Windows/NVIDIA, Fusion-page OpenFX. Keep a native C++ adapter thin and call the same Python/PyTorch engine through a versioned worker protocol if SDK investigation supports it. Analyse/cache a shot, then serve deterministic RGB+alpha frames; do not assume arbitrary separate output clips or shared GPU buffers. Confirm host/SDK capabilities before promising controls or background analysis. The official CorridorKey project already provides its own plugin.

Design requirements: deterministic shot/window identity, isolated per-instance models/caches, recurrent-state checkpoints, safe recomputation, synchronized concurrent requests, cancellation, worker crash handling and bounded memory shared with Resolve. Random, reverse, trimmed and retimed access must never depend on one mutable previous-request state. Key caches on source/timebase, proxy/resolution, colour boundary, weights/config/corrections and temporal policy. Invalidate on any change.

Validate sequential/random/reverse access, multiple instances, trims/retimes, proxies/resolution switches, managed-colour projects, viewer/export agreement and worker failure. Keep downloads, benchmark UI, asset management and training in companion tooling. No Apple GPU backend exists; macOS inference/plugin support is not claimed. Review repository and dependency terms before distribution/integration. Milestone27 now vendors a pinned official OpenFX interface-header subset; target Resolve-specific SDK/host capabilities remain unverified.

## Primary SDK investigation — milestone26

The official [OpenFX rendering reference](https://openfx.readthedocs.io/en/main/Reference/ofxRendering.html) defines host-requested render actions, sequence begin/end boundaries, arbitrary render windows and concurrent render calls governed by the advertised thread-safety property. Sequence callbacks describe a requested range; they do not prove that a full shot has been analysed or cached. Initial adapter design should serialize its own instance processing and advertise only safety actually implemented. Separate instances still need explicit ownership/resource arbitration. This is a design inference from the API contract, not verified Resolve behavior.

The [OpenFX images/clips reference](https://openfx.readthedocs.io/en/main/Reference/ofxImageClip.html) documents temporal access properties, RGB/RGBA/alpha components, integer/float pixels, image bounds and signed row strides. Therefore a thin C++ adapter must translate host image bounds/orientation/stride and alpha association explicitly, request supported temporal access, and handle unavailable frames. Do not assume packed top-down RGBA, full image availability, arbitrary extra output clips or direct GPU buffers. Managed source primaries/transfers and host extensions still need explicit investigation.

The proposed first working path remains companion analysis/export followed by deterministic cached RGB+alpha serving. Bind a completed immutable cache to source/timebase, render scale/proxy, selected range, colour contract, weights/config/corrections and implementation identity. An arbitrary request reads its verified frame independently of previous requests; a miss is explicit, not a stale previous matte. Full-shot recomputation through the existing engine preserves chronology when no checkpoint is usable. Host input acquisition, request-time mapping, abort/lifetime, instance duplication and cache invalidation require actual SDK/host integration, not just a new JSON action name.

The public [Blackmagic support page](https://www.blackmagicdesign.com/support) fetched during this run exposed dynamic download placeholders rather than Resolve-specific OpenFX SDK capability documents. Consequently Resolve/Fusion-specific controls, background host access, temporal scheduling, GPU sharing and SDK version compatibility remain NOT VERIFIED. At milestone26 no native adapter or host build had been implemented by this investigation. Next obtain/inspect the target SDK and installed host documentation, build against the official headers, and test sequential/random/reverse/multi-instance requests, trims/retimes, render scales, colour and viewer/export agreement on Windows/NVIDIA. The generic OpenFX specification is evidence for API contracts only.


## Milestone27 working path

`native/ofx/adapter.cpp` now implements an experimental filter against pinned official OpenFX headers. The existing shared engine produces completed native EXR foreground/alpha; `python -m corridorkey.ofx_cache` seals those actual bytes for deterministic random/reverse cache reads. Native ABI/host-suite tests cover separate instance setup, signed/padded strides, premultiplication, cropped windows, image leases, cancellation/refusal and malformed/corrupt frames. Address/undefined-behavior sanitizer tests use independent nonuniform signed-HDR fixtures. These tests are local Clang/CPU verification, not Resolve or pretrained GPU acceptance. Detailed contracts, limits and commands: [ofx-cache.md](ofx-cache.md).

The adapter does not invoke inference inside host renders, acquire earlier source images, authenticate a same-geometry host source or automatically analyse/invalidate shots. Prepared-cache selection/time/colour matching is explicit and requires target validation. Native Windows build/loading, actual Resolve controls/instance duplication/lifetime, real footage, host-managed colour/export, retimes/proxies and GPU resource interaction remain NOT VERIFIED. This is an initial usable data path, not completion of the full integration objective.
