# Durable desktop queue and verified recovery controls

The optional desktop now has **Queue history…** and **Recovery…** windows. Launch with `python -m corridorkey.desktop` in the compatible environment with `requirements-desktop.txt`. This feature uses the existing `DesktopBridge`/`WorkerClient` and recoverable controller. It does not create another model engine, CPU/MPS inference backend, network listener or automatic job resubmitter.

## Durable observations and reopening

The default workspace still uses a session-only queue. In Queue history choose **Create queue…** and an existing parent; the app creates a private `queue-UUID` child. Use a location separate from input/hints/corrections, render destinations, model assets and recovery cache. Creation requests activation for future jobs. **Open history…** reads an existing owned workspace without activation or execution. **Use for new jobs** explicitly activates it. Finish/cancel current rows first; activation stops the existing worker/queue owner, waits for its cleanup, then opens the new writer. An actual ownership-lock error is surfaced, not treated as a stale PID or permission to delete a lock.

One SQLite exclusive lock connection owns the queue writer; independently committed queue data records requests and observations. The lock is released by actual process exit. A newly acquired lock proves no other writer holds that queue lock; it does not prove all old workers/descendants stopped. The app never kills or restarts a historical PID from a file. Old parent/worker PID, generation, session close flags and response records are historical metadata, not live-process authority. Normal New worker retains the selected journal and never resubmits old requests. It rechecks ownership after polling to avoid replacing a bridge activated by an asynchronous UI operation.

Requests are normalized/snapshotted before entering the bridge command queue. For durable render/recover operations, the owner commits the request before worker dispatch, then records dispatching/local-send phases. The UI's **recorded** event acknowledges persistence; **sending** is only local admission. A crash before persistence may lose an unacknowledged local operation. Dispatch intent without a later terminal observation remains unresolved, because a crash may occur before or after actual execution. Terminal worker events commit before reaching the UI. Progress persists at most every0.25s while UI progress remains coalesced. Cancels/status controls are not new inference jobs.

A failure before dispatch rejects the operation without starting it. A persistence failure after send cannot be called a rejection: the peer may already execute. The supervisor stops/drains its owned worker and preserves an authoritative terminal outcome or explicit loss/uncertainty. Storage failure while saving a terminal event may leave outputs complete but the durable state unresolved; inspect/recover deliberately. Shutdown also records cancellation of still-local, undispatched render/recover commands where storage is available. Cleanup attempts worker and database closure, retaining failure rather than claiming a clean durable shutdown.

History shows the latest128 saved rows. `result` is labelled an **observed result; outputs unverified**; old nonterminal phases are unresolved. Inspect selected validates request/event checksums, structure and matching metadata, plus managed batch-snapshot bytes where available. This does not recheck output inventories, source/model identity or current process state. A readonly metadata listing alone is not completion evidence. Load render settings fills the form using the original output parent, without submitting; Add render later creates a fresh UUID child. Clear finished removes visible rows only; it does not delete durable records or outputs. Loading recovery settings fills the recovery controls, again without submission.

Ownership markers and recorded metadata are local integrity/ownership guards, not a security boundary against deliberate external edits. Keep source/hint/model/document/asset files stable while work is queued/running. New GUI-authored correction saves retain their immutable paths; outside files can still change and must pass core verification. Reopening a history never recreates all old jobs as live queue entries, infers PID death, automatically resumes or overwrites earlier outputs.

## Actual recoverable batch workflow

Select **Recovery…**, an existing schema1 inference-batch manifest, a separate empty/owned recovery-cache workspace, and an exact nonnegative byte budget. All jobs must already request EXR and explicit scheduling (`auto_vram=false`); the UI rejects incompatible settings instead of switching formats/profiles. Existing flags enable durable IID MoGe/C-RADIO, chronological RVM/state and Hann event replay independently, default off. These use the existing runtime contracts and remain opt-in. Production still requires local CUDA/model/foundation/stat assets.

A durable queue must be active. **Run batch** submits a new recoverable request. For a previously journaled batch choose **Verify / resume** explicitly. The owner snapshots the parsed batch into its private `batches` directory, resolves relative inputs/hints/corrections/temp/weights/output paths, validates through the existing batch/core API and normalizes complete settings before the first publication. The snapshot's content hash is stored with its request. Later edits to the original manifest cannot change an accepted queued batch. Media/weights/correction assets themselves are not copied or globally locked. Optional legacy queue records without a batch hash remain historical observations; newly submitted recovery requests get managed snapshots.

Run/resume uses the same FIFO worker as ordinary renders. Switching from a resident normal session to recovery closes that session; recovery retains its existing fresh-batch lifetime and asset/context binding. Worker progress/cancellation remain actual shared events. Select a main queue row to cancel it, or Cancel current in Recovery for the most recently tracked request. Batch results reference the complete local report, not a fabricated single-image result. Main single-job export preview deliberately directs recovery rows to their per-job report paths.

Only the existing recovery controller validates completion: hashes/full native EXR inventory and context checks determine `verified_existing`, `verified_cache_restore` or fresh `render`. Corrupted/missing outputs are not relabelled complete. Restores/recomputations get fresh destinations and preserve prior/partial/user outputs. A zero sealed-cache budget disables stored bundles but still allows verified journal/output resume. Changing cache policy/settings can invalidate reuse; no skip or speedup is promised. The actual controller/report rules and native-call/platform limits are in [recovery.md](recovery.md).

Inspect report reads the saved controller report; Open report also permits failed/cancelled reports written before a worker error. Workspace metadata lists up to128 journal/report paths with payload/backend/outputs explicitly NOT VERIFIED; it does not open a controller or prove owner absence. Only a new explicit verification/resume operation revalidates output eligibility. Raw origin timings remain historical and byte replay is not new neural FPS. The report viewer prioritizes recorded kind/status/note/error/jobs without modifying the saved file or computing missing metrics.

## Storage, ownership and bounds

A queue uses an owned marker, writer-lock database, separately committed data database and managed batch snapshots. SQLite full synchronization is requested; actual process-crash release and persistence are tested. Directory/power-loss guarantees and Windows storage/containment remain NOT VERIFIED. Opening an unowned directory rejects without changing its user files. Read-only inspection explicitly closes connections; invalid markers/symlinks, metadata/hash disagreement and oversized snapshot bytes fail. The optional `batch_hash` column is added under exclusive ownership for earlier queue-schema1 stores; existing observations are preserved.

Admission is4096 requests per queue; after that create a new workspace. Request/event frames and canonical batches are bounded4MiB each; markers and batch reads apply raw byte bounds before whitespace normalization. The headless batch loader now shares strict4MiB/128-depth duplicate/finite/exact-integer-version validation. Existing valid aliases/settings/relative paths are retained; schema booleans and ambiguous/nonfinite JSON now reject. Report inspection is32MiB/128 levels with a2Mi-character displayed view and explicit truncation notice. Historical headers/page size, bridge commands/events and worker transport have their existing independent bounds.

These are admission/inspection bounds, not a total RAM/VRAM or physical disk budget. Request history, database/journal overhead, prepared/unreferenced snapshots, reports, cached render copies, source/model files, serialization buffers and native processing allocations remain separate. At maximum frame sizes,4096 request/last-event pairs could retain roughly32GiB of JSON before other overhead; ordinary records are smaller. Durable observations/snapshots are not silently evicted. Cache byte controls affect only the recovery controller's managed sealed entries, not queue history or all disk use. Paging/filtering/archive/resource UX and broader stress acceptance remain work.

The main window waits asynchronously for queue/report I/O and owned worker/editor/benchmark shutdown. Native filesystem operations cannot be forcibly interrupted by the inspection thread. Uncertain cleanup blocks automatic ownership transitions; independently started applications/CLIs remain outside this app-local scheduling gate.

## Read-only history pages

History now exposes Newer/Older pages with at most128 headers per page; Refresh returns to latest. A SQLite admission-sequence cursor keeps forward traversal stable when timestamps tie or new requests arrive. No event payloads are loaded for the entire history: selected detail still uses the existing bounded checksum/schema inspection. Navigation/inspection never activates a journal, submits work, infers old PID state or validates current outputs. Saved observations remain historical; active-owner changes can appear on a later read. The current writer still admits4096 retained requests; paging does not delete/archive them or expand that limit. Archive/retention management and physical disk quotas remain unfinished.

Actual regression coverage traverses270 records despite equal timestamps and a concurrent new admission, with no duplicates/skips; Qt tests cover older/newer/refresh/oldest detail and zero submissions. The generated demo visits128/128/14 headers and leaves the source database byte-identical.


Milestone24 adds [sealed history and fresh queues](queue-archives.md). Managed writes are permanently refused for a sealed root; old data stays in place and can still be inspected or deliberately loaded into a new request. Rotation does not expand per-workspace admission or delete anything, and failures do not imply that a seal rolled back. Physical quotas/deletion/export remain open.
