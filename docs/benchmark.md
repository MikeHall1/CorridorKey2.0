# Benchmark specification and commands

Run `python3 -m corridorkey.benchmark` from the repository. Optional flags: `--manifest PATH`, `--output PATH`. Schema version 1 supports `kind: cpu_correctness` and `kind: inference`, with at least three repetitions. CPU manifests launch the real unittest suite each repetition. Exit status is nonzero on test failure. Reports default to ignored `benchmark-results/cpu.json`; no uploads occur.

CPU manifests optionally set `timeout_seconds`, a finite numeric value greater than zero and at most 3600; booleans are rejected. The default is **600 seconds per test subprocess**, replacing the previous 120-second limit. Reports retain `cpu_timeout.requested_seconds` (null when omitted), `effective_seconds` and the per-subprocess scope. Timeout fails the benchmark, retains completed repetition records and leaves aggregate times null; it does not silently shorten or skip tests.

Report fields include commit, dirty status and a content hash covering tracked/untracked nonignored source, manifest SHA256, installed dependency versions, Python/OS, available CPU/RAM/storage information, asset SHA256 identities, filesystem/model cache states, raw subprocess results, median and range. Unsupported telemetry is null or explicitly unavailable. CPU test duration is not model performance. In CPU reports, inference FPS, model throughput and quality are null. CPU results remain distinct from inference measurements. Inference manifests now use the persistent session/core (details below). Optional alpha reference metrics and EXR export comparisons are implemented below. Alternating performance A/B automation, model-only throughput, process-tree/power telemetry remain unimplemented; the optional desktop benchmark UI is described in [developer-benchmark.md](developer-benchmark.md); declared motion-compensated temporal alpha metrics are implemented below. Cooperative cancellation is available in the shared session/batch API; the desktop benchmark supervisor also owns cancellation and child cleanup. Interrupted benchmarks retain available records but do not resume measured repetitions automatically.

## Report destination safety

The benchmark CLI admits its report destination before starting work and revalidates it before publication. It protects suite/batch/quality manifests, referenced inputs and corrections, selected model assets, declared job outputs and the actual generated artifact directory. The general artifact parent is not reserved. Suite, batch and quality metadata reads are bounded to 4 MiB; changed dependency bytes or path resolution invalidate publication. Invalid or incomplete dependency inventories leave the report unwritten and preserve any existing destination. An unrelated regular report file may still be replaced deliberately.

Admission rejects aliases, special files, linked model trees and inventories exceeding its scan bounds. Missing model assets do not themselves require installation just to establish protected paths. Conservative Unicode-normalized, case-folded comparison can refuse distinct names on a case-sensitive filesystem. These sampled checks protect ordinary local workflows; they are not a reservation against hostile concurrent filesystem changes.

Planned local asset inventories live in `benchmarks/suites/required-assets.json`. They are inventory manifests, not runnable inference suites. Real assets are missing. Development and held-out footage must be separate, with provenance and usage recorded. Synthetic fixtures cannot supply professional quality evidence.

Generate a tiny 17-frame moving soft-rectangle RGB/alpha fixture with `python3 -m corridorkey.fixtures --output benchmark-results/fixtures`. It writes PNG sequences and provenance/FPS metadata; existing destinations are rejected to avoid stale frame mixing. No neural model runs. Optional `tests/test_io.py` exercises real OpenCV/PyTorch CPU adapters and EXR roundtrips, and skips explicitly when those dependencies are absent. Current compatible CPU verification uses `python -m unittest discover -s tests -v` (Python3.12/NumPy1.26); the earlier NumPy2 test-only environment remains historical evidence in `baseline.md`.

The complete inference protocol calls for requested/effective config, seeds, weight/foundation hashes, source/hint/correction identities, dimensions, timing, colour interpretation, format, hardware/driver/CUDA and power settings, budgets/cache policy, errors and warnings. The runner records the implemented subset below; power settings and total process/disk budgets remain unavailable. Correction inputs now have manifest, canonical document, source and actual asset hashes. Foundation RAM payload limits and automatic VRAM selection budgets are now recorded. Use GPU events/synchronization for asynchronous stages, wall clock for job elapsed time, process-tree resource sampling including encoders, and separate detailed profiling from throughput runs.

Report startup/model load, warm first usable frame, uncached throughput, decode/output-inclusive throughput, request latency percentiles, buffering and look-ahead, cached playback and causal-live latency separately. Record peak allocated/reserved and whole-process VRAM, process-tree RAM, temp storage, disk I/O, cache hit rate, success/recovery and batch completion. Overlapping stages are not additive wall time.

Initial target case is configurable 1920x1080 at 24 fps; also evaluate 1080p30/60, 1440p, 4K24/30 where hardware fits. No hardware-independent guarantee. For a direct comparison: fixed hardware/assets/settings; manual selection and automatic selection separately; cold processes and warm workers separately; cache conditions stated; warm-up where appropriate; >=3 measured repetitions alternating baseline/candidate order; median and variation with raw times; individual changes then combination. Speedup = baseline elapsed / candidate elapsed. Test without encoding and realistic export separately. Numerical tolerance must be chosen before judging based on repeatability/precision. This increment is a reliability fix, with GPU behavior preservation unverified.

## Inference benchmark modes (implemented, GPU runs unmeasured here)

Edit the local input path in `benchmarks/suites/inference-batch.example.json`, install/validate the CUDA environment and weights, then run:

```sh
python -m corridorkey.benchmark --manifest benchmarks/suites/inference-cold.example.json --output benchmark-results/cold.json
python -m corridorkey.benchmark --manifest benchmarks/suites/inference-warm.example.json --output benchmark-results/warm.json
```

An inference manifest has schema_version 1, kind `inference`, a relative/absolute `batch_manifest`, explicit `model_state` and >=3 repetitions. `cold_process` creates a fresh Python child per repetition and includes startup/import/load/job/teardown wall time. Jobs within that child share one model. The supervisor does not initialize a competing CUDA context. `warm_session` uses one in-process session, executes a full unmeasured warm-up job for each batch input, then measures the requested repetitions; warm-up job records (including initial load time) are separate. This is uncached computation with a loaded model, not cached playback. Filesystem caching is uncontrolled and hashing itself reads assets before measurements. No filesystem cold-cache claim is made.

Preflight reads, hashes and parses one bounded batch snapshot. Cold-process child manifests use only its validated immutable jobs, including writer settings and profiling flags; later edits or appended jobs in the original batch do not alter execution. Each run receives fresh output directories beneath ignored `benchmark-results/inference-*`; exports and child logs are retained for review. This intentionally measures realistic output writing; a no-encoding/model-only path is not implemented. Profiling synchronization is prohibited in throughput manifests. Reports contain source/hint/weight hashes, working-tree/manifest identities, dependencies, hardware/driver where available, raw job records with source/precision/hint/config/output/cache metadata, and median/min/max process or batch times. Asset hashing, telemetry collection, manifest preparation and warm-up are outside measured durations. Failed prerequisites/jobs produce failed/unavailable records with null inference/quality metrics, never fabricated throughput. Correctness branches are CPU-tested with test doubles; this is not successful neural inference.

Cold and warm results describe different conditions and are not an optimization speedup comparison. Continue to alternate baseline/candidate order externally with identical hardware/assets/settings, and evaluate automatic settings separately. CPU test-only NumPy 2 validation does not validate the declared CUDA/NumPy <2 stack.


For the opt-in feature-reuse experiment, change only `foundation_cache_mb` between otherwise identical manifests and keep temporal window/batch/output settings fixed. Job diagnostics now record actual IID frame requests/evaluations, hits/misses, retained RAM payload peaks and logical copy bytes, and optional automatic VRAM selection policy. See `feature-cache.md`; counts alone do not establish speedup. Cache instances are per job even in warm sessions; there is no cross-job/output playback reuse. Benchmark `cache.intermediate` remains per-job-only, with RAM reuse described by each job's effective settings and diagnostics.


Offline Quick Key benchmark settings use `quick_key`, `quick_interval`, `quick_context_radius`, `quick_flow_max_side`, `quick_fallback`, diagnostic thresholds and supplied `quick_cut_frames`/`quick_reset_frames`. Keep full-rate interval 1 as a separate reference and compare propagated-alpha loss separately from source-RGB foreground substitution. Job records expose actual Stage 1 context frame instances, Stage 2 evaluations, chronological RVM work, flow cost and neural fallback frames. Low-VRAM IID prepasses still cover all frames; adaptive/max-gap/hold/causal controls are implemented, while a live streaming runtime and latency budgets are not. Per-frame local JSONL traces are rendered-attempt diagnostics, not durable output completion. CPU fixture counts establish neither neural output quality nor net GPU speedup. See `quick-key.md`.


New optional Quick Key settings: `quick_auto_cuts`, `quick_cut_threshold`, `quick_analysis_max_side`, `quick_max_gap`, `quick_adaptive`, `quick_motion_threshold` and `quick_approach` (offline/hold/causal). Keep analysis on/off, adaptive on/off and approach results separate; analysis adds a full decode pass and causal RVM uses one-frame chunks. Explicit neural fallback is required for adaptive mode; no adaptive hold mode is exposed. Record supplied/detected/effective cuts, scan costs, planned/actual/promoted anchors and reasons, per-stage neural work, motion cost and fallback count. Causal propagation has no future matte read, but full-clip precompute remains offline. The CPU changed-future test is correctness evidence with neural substitutes, not proof of real-model causal quality or latency.

`benchmarks/suites/quick-key-matrix.example.json` provides 26 local cases: intervals 1,2,3,5,8,10; offline/hold/causal where valid; adaptive off/on where supported. `quick-key-warm.example.json` runs them through the existing >=3-repetition warm-session harness. Replace input/weights with permitted local assets before use. This declares cases, not automatic alternating A/B order or quality measurement; no GPU matrix has been run here.

Correction-enabled benchmark jobs use `settings.corrections_path` relative to the batch manifest. Reports verify and fingerprint the canonical document, actual manifest bytes and local assets before measured runs. Each session still revalidates source/assets per job; `correction_preflight_seconds` is separate from processing FPS but included in session elapsed/batch wall time. Correction files/hashes/frames/strength/ranges/resets must be identical for a timing comparison unless they are the experiment under study. Authored-output effects are CPU-tested, not measured GPU/model quality.


Colour/refinement comparisons must record source transfer/primaries assumptions, observed decoded dtypes, explicit alpha association and all optional spatial/despill controls (`colour.md`). Model/foundation bfloat16 input remains unchanged. Alpha data does not receive RGB transfer; compare premultiplied/straight cutouts using the matching linear composite equation. Refinement wall time/counters are reported separately but included in processing/batch costs; no current counters imply accuracy or GPU speedup. Host EXR metadata/encoded video and photographic references remain unavailable. High-bit video/managed source transforms are still pending.

## Optional alpha reference manifests — milestone 10

Inference manifests can supply `quality_manifests`: one alpha-sequence manifest path or null per batch job, relative to the inference manifest. See `benchmarks/suites/inference-quality.example.json` and `alpha-sequence.example.json`; example paths/provenance are placeholders and no assets are bundled. Jobs requesting evaluation must export EXR alpha explicitly. No preview-video fallback or additional output is enabled automatically. Existing inference manifests retain null quality when this field is absent.

Preflight validates schema, role/path consistency and provenance, checks reference/baseline/mask files, pins their content hashes, and binds each template source to its batch job. Candidate paths in a benchmark template are replaced by the completed job's actual native EXR alpha exports. Frame IDs are **zero-based output-relative indices**, including for trimmed sources; they are not absolute source-frame numbers. Choose reference filenames for that output range explicitly. Source start-frame metadata is retained in candidate binding. No source-offset alignment, VFR correspondence or optical-flow alignment is inferred.

The adapter requires a successful job, declared one-channel coverage EXR, actual native output FPS matching the manifest, decoded output geometry matching job metadata, output ownership, and every submitted frame exactly once. It recognizes full-rate `alpha_NNNNNN.exr` and Quick Key `alpha_source_rgb_draft_NNNNNN.exr`; unexpected/duplicate/missing files or out-of-range selected IDs fail. Source changes and changed reference/baseline/mask hashes fail rather than mixing experiments. Candidate/reference/valid-mask hashes and author/origin/permitted-use/split declarations accompany every result.

All quality decoding/hashing/metrics execute **after all measured inference repetitions**, outside their recorded elapsed times. Cold-process and warm-session paths share this post-processing step. Per-run/job reports under `inference.quality` distinguish candidate accuracy from baseline comparison: reference-only accuracy can be measured while comparison is unavailable; partially supplied quality manifests yield partial status. Reported quality-data failures make the summary unsuccessful while retaining completed inference timings. An exception during quality evaluation also makes the summary unsuccessful and records `inference.status=unavailable_or_failed`; interruption records `cancelled`. Neither path reports overall success merely because inference repetitions finished. Missing references never become zero error. Foreground/composite integration is implemented below; source-RGB substitution and other tradeoffs remain unmeasured on real footage.

Tests use generated EXR files and the real shared session/writer with a neural substitute to verify export/report plumbing, hash stability, full/draft naming, FPS/geometry/source/count guards and error separation. They do not prove CUDA availability, model output quality, inference throughput or the cold-process CUDA runtime. Real GPU/weights/permitted footage acceptance remains external. Automated alternating baseline/candidate performance runs, process-tree/power sampling and other quality metrics remain future work.

## Optional foreground/composite comparisons — milestone 11

`quality_manifests` now accepts either alpha or `colour_sequence_evaluation` manifests per job. `benchmarks/suites/inference-colour-quality.example.json` supplies the schema example. Existing alpha manifests keep their behavior. Colour templates declare `candidate_output: fg` (default) or `cutout`; the corresponding RGB output and alpha must already be requested as EXR. Preflight rejects output/layout/association mismatches rather than enabling outputs or selecting a substitute. For premultiplied cutout use matching job `cutout_alpha_mode`/linear settings and candidate RGBA layout/association in the template.

Binding validates complete native RGB and alpha timelines, owned output directories, source/FPS/geometry, scene-linear RGB and the runtime's declared assumed sRGB/BT.709 primaries, plus straight/premultiplied cutout association. Full and `_source_rgb_draft` names are recognized, including premultiplied cutout names. This checks the engine's stated assumption; it does not independently certify real source primaries or host interpretation. Native fg is straight; cutout uses its declared association. Reference IDs remain zero-based output-relative, and each role's recorded file hash/linear interpretation is explicit.

All reference RGB/alpha/masks/background asset hashes are pinned during untimed preflight and checked against actual reads. Quality executes after measured repetitions. Foreground/composite errors and alpha accuracy accompany candidate/baseline reports; partial/missing metrics remain labelled and quality failures retain measured inference timing/status. Existing benchmark integration tests use a neural substitute; actual generated foreground/premultiplied-cutout EXR tests prove binding/math only. No GPU/model performance or photographic quality results are claimed. Declared temporal alpha evaluation is implemented below; automatic alternating performance comparisons and held-out/blinded acceptance are still pending.

## Temporal reference manifests — milestone 12

`quality_manifests` can also select `temporal_sequence_evaluation` per job. Example: `benchmarks/suites/inference-temporal-quality.example.json`. Explicit EXR alpha output is required; native completed-output binding, source/FPS/geometry/ownership/completeness checks, fresh run directories and post-timing evaluation are shared with alpha/colour paths. No extra render output, flow estimation, temporal approximation or decoding fallback is enabled automatically.

Preflight pins all external reference/baseline/mask/flow/visibility hashes. Candidate-independent provenance, current-to-previous native-pixel convention and preceding selected-frame links are explicit. Reference IDs are output-relative, including trimmed sources; FPS alone is not encoded/VFR or correspondence proof. Benchmark adapters check effective Quick Key cuts, requested cuts/resets and authored shot/reset metadata: any selected pair spanning a known runtime boundary must be marked `cut:true` and omit unused flow/visibility assets. Unexpected detected boundaries fail quality evaluation until the reference specification is corrected; processing timings remain available.

Temporal residuals and spatial alpha accuracy are reported together, with population-weighted aggregation, cut/unavailable-pair counts, diagnostic changes and per-pair metadata. Partial/missing reference data remains labelled. Changed flow/visibility invalidates the experiment. Real generated EXR tests prove binding/cut/error transport only; independent flow accuracy, photographic/held-out quality and actual GPU timing are not established. Multi-report evaluation per rendered job, broader generated/photographic stress suites, alternating performance automation and process-tree/power sampling remain work.


Completed-job recovery/replay is a different workload from uncached inference. The opt-in `recovery` controller reports retained/restored bytes, current controller wall time and historical origin job records; do not interpret replay as neural FPS or mix it into cold/warm inference speedups. Current benchmarks still use fresh destinations and shared inference directly. `recovery.md` describes identities/limits and CPU work-count evidence; real GPU replay-vs-recompute measurement, power/process-tree budgets and intermediate resume validation remain future work.


Milestone19 adds actual per-repetition phase callbacks outside measured scopes, strict bounded finite/duplicate/version manifest parsing and CPU interruption/timeout report preservation. CPU reports now include top-level complete/failed/cancelled status. Aggregate CPU timing fields are null unless all requested repetitions succeed; completed raw records remain. The CLI returns130 on CPU cancellation. The optional desktop [developer benchmark window](developer-benchmark.md) runs this exact CLI with render-worker exclusion, process supervision, actual report/baseline inspection and exact-byte export. It does not implement alternating baseline/candidate experiments or invent missing metrics.
