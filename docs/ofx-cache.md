# Experimental completed-export cache for native OFX

The companion sealer reads an actual completed shared-engine record and its native EXR foreground/alpha outputs:

```sh
python -m corridorkey.ofx_cache --record /local/completed-record.json --output-parent /local/caches
```

It requires shared completed record schema1 and all recorded EXR exports to contain exactly the submitted indices, actual selected source geometry/count/start/FPS, scene-linear straight foreground and coverage alpha. It streams one RGBA frame at a time into a fresh private directory, verifies original EXR hashes again, preserves the record bytes and publishes `frames.ckcache` (or visibly labelled `frames-source-rgb-draft.ckcache` for source-RGB draft foreground) without replacing an existing target. Original media/exports remain unchanged. No inference, approximation or conversion to display RGB is introduced. These are current completed output bytes; a record with path-only model/source metadata is not authenticated original producer provenance.

Version1 is a little-endian binary file. Prefix `<8sIIIqd32s` contains CKOFX001, width, height, count, source start, FPS and SHA256 of the preserved completed-record bytes. A32-byte digest of prefix+frame table follows, then count32-byte frame hashes, then packed top-down straight scene-linear float32 RGBA frames. Frame hashes bind record identity, relative frame index and exact payload. Native reads verify complete file size, header/table hash, selected frame hash, finite RGB and [0,1] coverage before use. Indices can arrive in any order; no mutable previous frame or temporal-state reconstruction exists in this reader.

Bounds: max1,000,000 frames, max16,777,216 pixels/256MiB payload per frame, up to32MB digest table. These are admission bounds, not total application/process/disk budgets. Cache creation duplicates selected exports and has no automatic retention/deletion. A failed seal removes only its owned staging file; its private directory/record may remain. Unsupported hard-link/filesystem behavior fails explicitly. Header/file checksums detect accidental changes; they do not authenticate an adversarially replaced whole cache or validate the host's source selection. Directory-entry power-loss durability is not proven by file fsync.

The official OpenFX header subset and BSD3 licence are pinned under third_party/OpenFX. Direct local Clang native tests are not Windows Resolve acceptance, CMake execution, real neural quality or GPU performance. Managed host primaries/transfers, original source matching, retimes/proxies and actual host behavior require further validation. The full project remains incomplete.

The experimental filter adapter is `native/ofx/adapter.cpp`. It exports the real OFX enumeration/entry ABI and defines Source/Output float RGBA clips plus CacheFile and CacheStart parameters. CacheStart explicitly maps cache index0 to an integer host frame time; it does not infer Resolve trim/retime offsets from source_start. Render requests must be integer indices within the cache, native scale, unfielded and square-pixel; source RoD/origin/FPS must match cache dimensions/timing. Actual output image metadata must be premultiplied float RGBA. Top-down cache rows map to OFX bottom-up rows through the host's signed byte stride, and only the requested in-bounds window is written. RGB is premultiplied by coverage without display clipping. Host image handles are scoped and released on success/error/abort.

Rendering is conservatively serialized across instances and advertises RenderUnsafe/no host frame threading. It does not request temporal Source images: chronology/analysis happened in the companion engine, while this adapter reads a completed cache directly. No source RGB is sampled to authenticate that a same-geometry host clip is the original producer source. File selection and colour/source matching remain explicit user responsibilities; this is an experimental prepared-cache effect, not validated live keying or automatic host cache invalidation. Change cache selection/purge host outputs after external modification; managed immutable cache creation never overwrites the selected file.

Direct local compilation/test commands are exercised by the Python native tests. `native/ofx/CMakeLists.txt` provides the target build recipe, but CMake is absent locally and Windows compilation is NOT VERIFIED. The minimal suite host checks actual adapter callbacks and image leases; it does not emulate Resolve's implementation, GPU memory management or colour pipeline. Native file reads/checksumming can block before row-level abort checks; no hard interactive latency guarantee is claimed.


Target recipe (requires prepared Windows x64 CMake/compiler environment; not executed locally):

```sh
cmake -S native/ofx -B C:/local-builds/corridorkey-ofx -A x64
cmake --build C:/local-builds/corridorkey-ofx --config Release
```

Windows output uses `CorridorKeyCached.ofx.bundle/Contents/Win64/CorridorKeyCached.ofx` with licence/notices in Resources. [OpenFX packaging](https://openfx.readthedocs.io/en/main/Reference/ofxPackaging.html) specifies the Win64 architecture location. The recipe uses a generator-expression directory to avoid Visual Studio inserting a configuration subfolder, as described by [CMake RUNTIME_OUTPUT_DIRECTORY](https://cmake.org/cmake/help/latest/prop_tgt/RUNTIME_OUTPUT_DIRECTORY.html). The adapter rejects non-Intel-x64 Windows targets. No installer/system plugin directory is modified automatically. Both recipe execution and target host discovery remain NOT VERIFIED.

The source companion also has an explicit packaged-app dispatch route: `CorridorKey.exe --corridorkey-module corridorkey.ofx_cache --record PATH --output-parent PATH`. This command contract is source-tested; the packaged executable itself remains unverified. Desktop build data retains the OpenFX licence/provenance; it does not automatically bundle a native plugin built on another platform.

## Strict producer-bound caches (version2)

Opt in **Record exact source for bound cache** in Common job settings, or use `--source_witness` together with `--frame_dir_linear --output_format exr`. Default is off. Initial support requires an actual frame directory with exactly3 RGB channels, explicitly assumed scene-linear primaries and ignored source alpha. Video, implicit transfer conversion, RGBA/unpremultiplication and more than16384 selected frames are refused. This records pixels used during a new render; an old path-only record cannot be upgraded by hashing its source afterward.

Native linear float32 RGB is witnessed at the actual decode boundary before model/foundation precision conversion, including full/low-VRAM prepasses, temporal windows, shot analysis and current-source/anchor Quick Key reads. The first observation of each selected frame is retained; a later read of different pixels fails. Every selected frame must be observed before the witness is completed, after owned readers/writers are cleaned up. A private output sidecar records CKSRC001, geometry/count/sourceStart/FPS and32-byte frame digests. The completed record includes its hash/contract/path; missing/changed/incompatible sidecars fail preparation. This is consumed-source evidence, not cryptographic producer/model/settings authentication.

Version2 uses CKOFX002 with the same100-byte header layout. Each table entry is64 bytes: existing output-frame SHA256 followed by the corresponding source digest. Header digest binds the entire table. A source digest is SHA256 of `CorridorKey/source/linear-rgb-f32/v1` plus a zero byte, LE uint32 relative index/width/height, then exact top-down packed RGB float32 LE bytes. Signed zero remains bit-exact. No tolerance, quantization or hidden colour conversion is introduced.

The native effect declares temporal Source access and requests the complete selected mapped host range. Before acquiring/writing Output, **every selected Source frame** at CacheStart+i must have matching exact native RGB, opaque alpha1, supported floatRGBA association, native render scale, full geometry, square pixels and no fields. All frames participate conservatively because temporal/recurrent/cut processing can depend on neighbors. Wrong past/current/future pixels, mapping/colour differences or missing frames fail explicitly. Verification is repeated per render; notifications alone are not treated as a trustworthy source epoch. Source image leases release on failure/abort; hashing staging is bounded48KiB. Per-instance serialization advertises RenderInstanceSafe and permits upstream evaluation of another instance without the old global-lock deadlock.

This correctness reference costs O(selected frames × pixels) **per output render**. It is not real-time cached playback or a complete invalidation implementation. Exact-bit decoder/colour rounding may refuse visually equivalent sources. Pixel agreement cannot establish managed primaries metadata, expected companion parameter selection or actual Resolve invalidation of output already cached without calling Render. Actual host notification/project persistence/viewer/export/concurrent scheduling acceptance remains required. Legacy CKOFX001 is still the explicitly manual unbound workflow. The desktop notes distinguish records requesting a witness.

`benchmark-results/m29-bound-summary.json` records actual shared runtime CPU-fixture processing → producer witness → sealer → sanitized native host, source range[1,4), maximum output error0 and source/exports unchanged. Independent handcrafted HDR/source and4096-pixel boundary fixtures cover source mismatches, corruption, leases, strides and nested instances. CPU substitutes and an SDK harness are not pretrained/Windows/Resolve evidence. CK-OFX-02 remains in progress.

## Desktop preparation

Select a completed queue render, choose **Prepare OFX cache…**, choose an existing destination folder, then **Prepare new cache**. Opening the panel submits nothing. It snapshots the completed record, displays actual geometry/FPS/source range and foreground mode, and creates a new private preparation directory without changing the current form or queued job. Source-RGB drafts and explicit test-only records remain labelled. An invalid/rejected replacement clears the previous idle selection; queue actions require an actual highlighted row.

Hashing, path resolution, native decoding and sealing run on one owned background thread; progress is coalesced and terminal delivery is bounded. Cancel requests cooperative cancellation during validation, file hashing and frame conversion. Native codec/filesystem calls may delay cancellation. Panel/workspace close waits for the actual owned thread and terminal result; it does not drop ownership on a timeout observation. A complete cache path is published only after the hard-link commit. Late cancellation or failure to unlink the owned stage does not turn a committed output into a false failure; cleanup failures are logged and the stage alias may remain. Pre-commit failure preserves the original exception and annotates cleanup errors. Private partial preparation directories/records may remain and are not automatically deleted.

The shared reader's optional exact-channel check is additive: ordinary image decoding retains its previous defaults. Cache preparation requires both declared and actual foreground3/alpha1 layouts, finite RGB, coverage in [0,1] and matching geometry. Multichannel alpha is rejected rather than silently choosing a channel. `seal(..., control=JobControl(...))` provides cancellation/progress to companion callers; the existing CLI flags and version1 native file format are unchanged.

Local acceptance: `m28-generated-summary.json` records an actual Qt/worker/native-EXR preparation and native-reader check for source range [1,3), unchanged original exports/queued settings, one render submission and safe cancel/close. CPU neural substitutes are explicit. This does not add automatic host source/time/colour binding or establish Windows/Resolve compatibility. Validate actual source/time/colour correspondence and host behavior as described in [Resolve integration](resolve.md).
